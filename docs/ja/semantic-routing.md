# Jev モデルルーティング戦略

Jev は、固定比率、適応型、品質優先、コスト優先、プライマリ／バックアップ、総合スコアと並ぶルーティング戦略です。クライアントは通常の公開モデル名で TokenHub を呼び出します。TokenHub は Jev に最新のユーザータスクを分類させ、設定済みモデルを選び、既存の Provider アダプターを通じて実行します。Jev は最終回答を生成せず、Provider として登録する必要もありません。

## 設定と呼び出し

1. `auto-chat` などの公開モデルを作成し、承認済みの上流モデルへのルートを追加します。これは通常のモデルエイリアスです。任意の名前に任意の戦略を設定でき、名前だけで Jev が有効になることはありません。
2. **ルーティング → モデルルーティング戦略**で **Jev スマートルーティング**を選択します。
3. 既存ルートから候補モデルを選び、各モデルの適用条件、モデル選択の指示、既定モデル、最小信頼度を設定して適用します。
4. その公開モデル名で `/v1/chat/completions` または `/v1/responses` を呼び出します。両方でストリーミングを利用でき、ツールやその他の生成パラメーターは対象モデルへのリクエストに保持されます。

例えば、一方の候補で抽出と翻訳を、もう一方で複雑なコード変更を処理します。適用条件はワークロード評価に基づいて記述してください。モデル名だけでは品質を証明できません。同一 Provider とモデルの複数リソースアカウントは一つの候補にまとめられます。他の戦略も同じ公開モデルとルートの設定方法を使用します。

ルートの Provider または上流モデルを変更すると、Jev エディターは保存済みの候補順序を保持したまま候補を更新します。ポリシーを適用する前に、新しいモデルの適用条件を確認してください。カタログに条件がない場合は入力が必要です。

```json
{"model":"auto-chat","messages":[{"role":"user","content":"Explain this code change."}],"max_tokens":128}
```

```json
{"model":"auto-chat","input":"Explain this code change.","max_output_tokens":128,"stream":true}
```

## サーバー設定

Jev への外部呼び出しは既定で無効です。サーバーでプロジェクトを許可し、TypeSafe キーを設定します。

```dotenv
TOKENHUB_SEMANTIC_ROUTING_ENABLED=true
TOKENHUB_SEMANTIC_ROUTING_PROJECTS=prj_example
TOKENHUB_TYPESAFE_API_KEY=<server-side-secret>
TOKENHUB_TYPESAFE_MODEL=jev-1.13.0
TOKENHUB_SEMANTIC_ROUTING_TIMEOUT_MS=1000
```

許可リストはカンマ区切りの完全なプロジェクト ID です。空の場合は外部評価を許可しません。有効化時にキーまたは許可リストがなければ起動検証が失敗します。評価モデルは具体的なバージョンに固定します。タイムアウトは候補メタデータ取得と評価を含み、既定は 1000 ms、上限は 10000 ms です。各プロセスは同時に 8 件まで評価し、待ち行列や再試行は行いません。

## 選択とフォールバック

TokenHub は評価前に認証、クォータ検査、プライバシー処理、ガードレール、適格なレスポンスキャッシュを処理します。明示的な Jev 戦略を使用したエイリアスと、すべての `previous_response_id` 継続は結果キャッシュの読み書きを省略します。キャッシュには検証済みのルートバインディングがないためです。プロジェクトと API キーの制限、スコープポリシー、Provider の健全性、リソースの可用性、プロトコル対応で先にルートを絞り込みます。Jev はこの集合に残る明示的な候補のみを選択できます。

Jev はルートの優先度階層をまたいでモデルを選択します。同一 Provider とモデル内のリソース順序は既存のプランナーが決定します。有効な選択が閾値以上なら、選択したモデルのリソース、既定モデル、設定順のその他の候補を試します。フェイルオーバーは既存の再試行ルールに従い、Jev を再度呼び出しません。候補集合に含まれないルートは実行対象外です。

タイムアウト、評価サービスの障害、同時実行枠の飽和、不正な結果、`no_preference`、低信頼度では既定モデルを使用します。サーバー設定が無効、またはプロジェクトが許可されていない場合も、テキストを送らずに既定モデルを使用します。既定モデルが対象外なら設定順の最初の適格な候補へ切り替えます。対応可能な候補がない場合やカタログ取得に失敗した場合は 503 を返し、未設定モデルは選択しません。適格な候補が一つなら評価は不要です。

候補のカタログレコードは有効である必要があります。宣言済みのモダリティ、実際のプロトコルパラメーター、コンテキスト上限で適格性を制限します。他プロトコルのパラメーター名を同等とは扱いません。コンテキスト検査は保守的なシリアライズ済みバイト数の推定と出力トークン予算を使います。宣言がないことは能力や適性を証明しないため、Provider モデルメタデータを正確に維持してください。カタログの正規化では、Chat Completions の宣言に対して `max_tokens`、Responses の宣言に対して `max_output_tokens` を個別に補います。別の予算フィールドが宣言済みでも省略しません。明示的な宣言は保持し、リクエストのパラメーター名は変更せず転送します。同梱の GPT-6 Astra は `max_tokens`、`max_completion_tokens`、`max_output_tokens` を明示します。保存済みの Provider モデルは再インポートして宣言を更新してください。

既存のキャッシュ／セッションアフィニティとスティッキールートの順序を優先します。スコープ戦略が明示的にアルゴリズムを上書きする場合、Jev 評価を省略し、設定済み候補内でその順序を適用します。セッション識別子付きのリクエストでは新たな Jev 判断を行いません。ルートシミュレーターは Jev を呼び出さず、分類結果を予測できません。Anthropic Messages、埋め込み、画像 API は従来のルーティング動作を維持します。

## Responses の継続

Jev Responses リクエストでは、選択したルート、Provider とモデル、リソースアカウント、上流レスポンス ID を保存します。公開する上流レスポンス ID は変更しません。`previous_response_id` を使う場合は同じ API キーと公開モデルを指定し、再分類せず元のルートを使用します。後で戦略を変更してもバインディングは適用されます。バックグラウンド Responses は出力フックの承認後、公開ジョブ ID と上流レスポンス ID の対応付けをジョブの正常完了と同一トランザクションで保存します。処理中、拒否、キャンセル、実行権喪失のジョブはバインディングを公開しません。出力プラグインが ID を変更した場合は、その公開 ID を元の上流 ID に対応付けます。

詳細なルートバインディングは SQLite または PostgreSQL で共有され、30 日で期限切れになります。保護対象の各レスポンス ID には、元の ID、アカウント、プロンプトを含まない無期限の鍵付きハッシュマーカーを保持します。詳細バインディングの期限切れ後も別エイリアスからの再利用を拒否します。保存量は保護対象 ID 数に応じて増えます。全インスタンスで同一の安定したサーバーシークレットが必要です。期限切れ、Jev モデルでの不明な ID、候補の削除、元のルートの利用不能または権限喪失では HTTP 409 を返します。継続時も元のカタログモデルの有効状態、実際のパラメーター、モダリティ、コンテキスト上限を再検査します。不適格なら再分類やフェイルオーバーをせず 409 を返します。読み書きに失敗した場合は 503 です。継続時は別モデルや別アカウントへ切り替えません。元のルートが利用できなければ完全な入力で新規リクエストを開始してください。この保存期限は上流 Provider 自身の保持期間を延長しません。

## データ処理と課金

分類器には最新の適格なユーザーテキスト、選択の指示、候補 ID、上流モデル名、設定された適用条件のみを送ります。システム／開発者指示、アシスタント履歴、ツール定義と結果、メディア、認証情報、ヘッダー、任意のモデルメタデータは Jev に送信しません。処理済みの生成リクエスト全体は対象 Provider に保持されます。テキストが 8192 バイトを超える場合、ユーザーテキストがない場合、最新のユーザーメッセージに非テキスト要素がある場合は、切り捨てやメディア送信をせずフォールバックします。

固定エンドポイントは `https://api.typesafe.ai/v1/systemone` で、リダイレクトは拒否します。Jev は制約付き TypeSafe `Choice` を返し、TokenHub が候補と信頼度をローカル検証します。承認済みのワークロードだけに外部ルーティングを許可してください。初期閾値 `0.65` は評価の開始値であり、品質保証ではありません。信頼度は選択肢の分布で、タスク成功確率ではありません。

監査アクション `routing.semantic` はゲートウェイリクエスト ID に、選択／フォールバック、戦略、プロトコル、選択モデルと候補 ID、評価モデルのバージョン、信頼度と確率、評価トークン数、所要時間を記録します。ユーザーテキストや認証情報は含みません。生成リクエストログには実行した上流モデルが残ります。公開モデルの価格を引き続き適用し、選択モデルに応じた自動再価格設定は行いません。評価器の使用量は別扱いで、生成トークン数や顧客請求に加算しません。

## 管理 API と互換性

`PATCH /api/admin/model-routing-policies/{model}` は戦略、全ルート、モデル選択ポリシーを原子的に保存します。既存の 2 ルートを使う例です。

```json
{
  "strategy": "jev",
  "routes": [
    {"route_id":"route_fast","weight":100,"quality_score":50,"cost_score":50},
    {"route_id":"route_deep","weight":100,"quality_score":50,"cost_score":50}
  ],
  "semantic_routing": {
    "mode":"enforce",
    "min_confidence":0.65,
    "instructions":"Choose using the configured task criteria.",
    "default_candidate_id":"fast",
    "candidates":[
      {"id":"fast","provider_id":"provider_a","provider_model":"small-model","criteria":"Simple extraction and translation"},
      {"id":"deep","provider_id":"provider_b","provider_model":"reasoning-model","criteria":"Complex analysis and code changes"}
    ]
  }
}
```

Jev 戦略には `enforce`、明示的な指示、1～32 個の異なる Provider／モデルの候補、空でない適用条件、候補内の既定モデル、0～1 の有限な閾値の明示が必要です。指示は 4096 バイト、各適用条件は 2048 バイトまでです。候補 ID は一意で、`no_preference` は予約済みです。各候補は公開モデルの既存ルートを参照する必要があり、不正な設定では更新全体をロールバックします。

ポリシーは `Model.metadata.tokenhub_semantic_routing` に保存し、通常のモデル編集やカタログインポートで保持します。明示的な候補を持たない旧 `off`／`shadow`／`enforce` 追加設定は、再設定するまで従来の Chat 専用・同優先度の動作を維持します。コンソールは旧設定を表示します。通常の戦略を適用すると旧設定は無効になり、Jev を適用すると明示的候補で置き換えます。`semantic_routing` の省略は旧追加設定を保持しますが、明示的な Jev から通常戦略への切り替えでは省略時も分類を無効にします。`jev` には完全な設定が必要です。エイリアスが Jev を使用すると、サーバー管理の `response_binding_required` は true のまま保持されます。戦略変更後の新規 Responses もバインディングを保存・検証し、不明・別キー・期限切れの継続を拒否します。クライアントのポリシー更新でこのフラグを解除することはできません。

Schema マイグレーション 6 は永続テーブル `jev_response_bindings` と期限索引を追加します。起動時に追加マイグレーションを適用してからリクエストを受け付け、ベースライン Schema は書き換えません。通常の戦略を選べばルーティング動作を戻せ、サーバー設定で外部評価を停止できます。どちらも既存の継続バインディングを削除しません。バイナリのロールバックはデータベース互換性宣言に従います。強制するためにマイグレーション履歴やテーブルを削除しないでください。

## 検証と導入

合成テストは TypeSafe プロトコル、制約付き選択、設定検証と原子性、パラメーター互換性、候補制限、フォールバック、Chat／Responses のストリーミングとツール、継続の所有権とリソース固定、バックグラウンドジョブ、SQLite／PostgreSQL 永続化、UI 保存と再読込を検証します。実際の精度や本番レイテンシを証明するものではありません。承認済みテストプロジェクトで、ラベル付き例のタスク結果、追加時間、評価と生成の総費用を比較し、その後に許可リストを拡張します。

任意の実 API スモークは `TestJevRoutingClientLive` です。テストプロセスの環境だけに `TOKENHUB_LIVE_TYPESAFE_API_KEY` を設定し、`backend/` で `go test ./internal/server -run ^TestJevRoutingClientLive$ -count=1 -v` を実行します。生成 Provider を呼ばず TypeSafe に合成リクエストを送り、既定ではスキップします。

参考：[LangChain Jev harness](https://www.langchain.com/blog/building-a-harness-with-jev)、[TypeSafe API](https://docs.typesafe.ai/api)、[Choice](https://docs.typesafe.ai/primitives/choice)、[Confidence](https://docs.typesafe.ai/confidence)。
