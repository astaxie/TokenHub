# バックエンドのリファクタリング計画

このドキュメントは、`backend/internal/server` を小さなドメイン、トランスポート、永続化
モジュールへ段階的に移す計画を記録します。issue #169 の今後の実装計画であり、
アーキテクチャ文書は現在のランタイム構成だけを説明します。

## 計画の原則

- 各段階で既存の HTTP、認証、認可、永続化、トランザクションの動作を維持します。
- 永続化ポートは利用するドメインまたはアプリケーションパッケージが定義します。GORM 行モデル、HTTP DTO、データベースの責務はアダプターに置きます。
- 依存方向を明示します。ドメインパッケージは `server`、HTTP ハンドラー、GORM をインポートしません。
- 次の段階に進む前に、依存関係の変更、互換インターフェース、残作業、検証結果を記録します。

## 移行状況

以下は各段階の依存関係の変更、状態、完了条件、残作業の概要です。内部タスク番号は含めません。

| 段階 | 依存関係の変更 | 状態 | 完了条件 | 残作業 |
| --- | --- | --- | --- | --- |
| 0. 基準と制約 | 新しいパッケージ依存を導入する前に観測可能な動作を固定し、対象ディレクトリが安定してから依存チェックを追加する | 完了、依存チェックは延期 | 動作特性の一覧が完成し、依存チェックの設計を独立した PR で実装できる | 最終的なディレクトリ構成が安定してからチェックを追加する。それまでは有効なリポジトリゲートとして扱わない |
| 1. 業務モジュール | billing と reconciliation の呼び出し元を `server.Store` から利用側が定義するポートへ移し、その後 analytics のポートとアダプターを導入する | 進行中 | billing、reconciliation、analytics の本番経路が公開インターフェースを使い、`server` に業務実装が残らない | analytics の抽出、古い server 投影の削除、残りのテストの移行 |
| 2. Gateway、プロトコル、Provider | `server` をプロトコルと Provider の実装から `gateway`、`protocol/*`、`provider` の依存関係の組み立てへ変更する | 計画済み | OpenAI、Anthropic、Gemini のプロトコルアダプターと Provider 呼び出しが共通のゲートウェイ契約を通じて動作する | 契約を定義し、Provider 管理、呼び出し、プロトコルアダプター、ゲートウェイのエラー変換を移す |
| 3. Project と Routing | 認証、認可、クォータの准入制御、候補計画、ルーティング方針を `project` と `routing` のポートへ移す | 計画済み | ゲートウェイが ID、准入制御、候補計画にグローバルな `Store` を使わない | Project と API Key の状態、クォータの意味、ルーティング方針、フェイルオーバー計画を分離し、准入順序を維持する |
| 4. リクエストのライフサイクルとバックグラウンド機能 | リクエスト記録、使用量、監査、ペイロード保持、画像ジョブ、可観測性を `usage`、`image`、`observability` へ移す | 計画済み | `Server` がリクエストや worker のドメイン状態を所有せず、ライフサイクルと復旧の動作が変わらない | 使用量の書き込みと監査の意味を抽出してから、ゲートウェイの処理連携、画像 worker、テレメトリーアダプターを移す |
| 5. アダプターと依存関係の組み立ての整理 | HTTP アダプターと永続化実装を整理し、`server` を依存注入、ルート処理、プロセスのライフサイクル管理に限定する | 計画済み | 互換コンストラクター、古い Store 投影、移行 shim が削除され、最終的な依存グラフがチェックで強制される | 残りの admin と永続化アダプターを移し、依存チェックを追加し、issue #169 に照らして構成全体を検証する |

各段階には順序のある依存関係があります。段階 1 で analytics の境界を完成させてから
段階 2 でリクエスト経路を変更します。段階 3 はゲートウェイ契約、段階 4 は Project、
Routing、Usage の境界に依存します。段階 5 はすべての本番呼び出し元が移行してから
shim を削除します。

## 段階 1 で完了した作業

### Billing

先行する PR で billing ドメインとアダプターを抽出しました。ドメインは同期、再試行、
カーソル、スケジューラーの動作を所有します。残る server コードは、公開 billing
インターフェースへの移行が済んでいない呼び出し元に依存関係の組み立てを提供します。

### Reconciliation アダプター

現在の段階では照合の永続化と管理 HTTP 処理を `server` から移します。

移行後の依存方向は次のとおりです。

```text
server -> admin -> reconciliation
server -> reconciliation/persistence -> reconciliation
```

reconciliation ドメインが `Store` と `BillingReader` ポートを所有します。`admin` は
リクエスト、レスポンス、CSV、監査のトランスポート変換を担当します。
`reconciliation/persistence` は SQLite と PostgreSQL の GORM 行モデル、トランザクション、
コスト証跡、請求データ投影のアダプターを所有します。依存関係の組み立て側は引き続き
データベースを開き、共有の永続化ミューテックスと監査コールバックを提供し、ルート認可を行います。

互換契約には既存の HTTP レスポンスとエラー、テーブル名とマイグレーション、帰属
スナップショット、明示的なゼロコスト証跡、ページング、CSV エスケープ、ロック、再計算、
監査の動作を含みます。PostgreSQL CI job はタグ付きの本番アダプター契約テストで
スナップショットの並行バックフィルを検証します。

残作業は、残りの server テストを公開モジュール境界へ移し、呼び出し元の移行後に
互換コンストラクターとテスト用投影を削除することです。

## 次の段階：Analytics

次の段階を個別にレビュー可能な二つの手順に分けます。

1. analytics のクエリとアプリケーションモジュールを抽出します。対象は analytics 認証情報、カーソルとスナップショットの意味、集計、利用側が定義する永続化ポートです。
2. SQLite/PostgreSQL クエリアダプターと管理 HTTP アダプターを移し、集計、認可、一貫性の動作を維持しながら server の analytics 実装を削除します。

analytics の本番経路が新しい公開インターフェースを使い、両データベースでアダプターが動作し、
本番呼び出し元がグローバルな server `Store` に依存しなくなった時点で完了します。

analytics の依存関係の変更は次のとおりです。

```text
server -> admin -> analytics
server -> analytics/persistence -> analytics
analytics -> usage (read-only usage projections)
```

認証情報のスコープ、カーソルとウォーターマークの意味、スナップショットの一貫性、
集計の境界、認可、ページング、クエリ制限を維持します。SQLite と PostgreSQL の両経路に
対象を絞ったテストがあり、既存 HTTP レスポンスの互換性が維持されていることが、
アダプター移行の完了条件です。

## 後続の段階

### Gateway、プロトコル、Provider

ゲートウェイ段階ではプロトコルに依存しないリクエストと結果の契約を導入します。
`protocol/openai`、`protocol/anthropic`、`protocol/gemini` が HTTP 表現を契約へ変換し、
`provider` が能力チェック、認証情報、上流トランスポート、ヘルス、エラー正規化を担当します。
ゲートウェイは具体的なプロトコルやデータベース型ではなく、Routing と Project のポートに
依存します。三つのプロトコル経路と Provider 呼び出しに独立した契約テストがあり、
`server` が登録だけを担当する状態でこの段階を完了します。

### Project と Routing

API Key 認証、Project 認可、RBAC、クォータの准入制御、並行数、候補計画、重み、
アフィニティ、フェイルオーバー、サーキットブレーカーの判断を `project` と `routing` へ
移します。ゲートウェイはグローバルな Store の読み取りから狭いポートの利用へ変わります。
認証順序、拒否時のステータスとヘッダー、クォータ予約と精算の原子性、候補順序、
レスポンスを送信し始めた Provider 呼び出しを再試行しない規則を維持します。

### Usage、Worker、可観測性

ライフサイクル段階では使用量、リクエストログ、監査、ペイロード保持、画像ジョブ、
Responses worker、トレース、メトリクス、構造化ログを抽出します。ゲートウェイの処理連携は
コマンドと投影を通じて呼び出し、行モデルや worker 状態を所有しません。使用量と監査出力、
リースと fencing、放置されたジョブの復旧、終了順序、可観測性ラベルが変わらず、
`Server` にドメイン状態が直接保持されていないことが完了条件です。

### 最終的なアダプターと依存関係の組み立ての整理

残りの admin と永続化アダプターを移した後、依存規則を実行可能なチェックにします。
互換コンストラクターとテスト投影は、最後の本番または動作特性テストの呼び出し元が
移行してから削除します。最終レビューには対象パッケージの依存グラフ、通過したリポジトリ
ゲートとバックエンドテスト、各永続化境界の SQLite/PostgreSQL 統合テストを示します。

各段階は同じ互換契約を維持し、この文書に依存関係の変更と残作業を記録します。
境界にデータベースの動作が関わる場合は、対象を絞った SQLite と PostgreSQL のテストを追加します。
