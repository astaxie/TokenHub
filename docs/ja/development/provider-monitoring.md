# プロバイダー監視の性能

## 問題と対象

以前は監視リクエストごとに過去30日間の観測をすべて取得し、Goでコピーとソートを行い、完了するまでプロバイダー一覧の表示を待っていました。Issue #425 は1,770,175件の観測と2回のOOM終了を報告していますが、このエンドポイントが終了の原因だったことは証明されていません。

## 修正設計

1. SQLでプロバイダー、観測元、UTC日付ごとに集計します。最古の部分日と将来日時の共通グループを含め、各プロバイダー・観測元につき最大32グループを返します。現在設定されているプロバイダーと対応する2種類の観測元のみが対象です。
2. 最新の観測1件と、成功かつ正のレイテンシを持つ観測の正確な下側中央値を取得します。直近24時間の窓、UTC暦日30日間の推移、古い観測・観測なしの状態、閾値、キャッシュ済みクォータの動作を維持します。最新時刻が同じ場合は観測IDの降順で決定します。
3. 集計、最新観測、中央値を同一の読み取り専用トランザクションで取得します。PostgreSQLでは反復可能読み取りを使用し、更新中の追加観測による不整合を防ぎます。
4. 各バックエンドプロセスで観測集計を15秒間キャッシュします。同じプロバイダー集合の同時リクエストは1回の更新を共有します。設定、リソース、ルート、クォータのスナップショットは再取得します。集合の変更時は旧キャッシュを使わず、失敗はキャッシュしません。
5. 共有更新には10秒の期限を設定します。HTTPリクエストのキャンセルで待機を終了し、最後の待機者がキャンセルするとDB処理も中止します。他の待機者がいる場合、その処理は継続します。DBエラーやタイムアウトは内部情報を含まないHTTP 503を返し、空の成功結果にはしません。
6. コンソールは監視を独立して読み込みます。待機中も一覧と操作を利用でき、失敗時は一覧を維持してエラーを表示します。再読み込み、画面離脱、セッションやバックエンドの変更、アンマウントで古い監視リクエストを中止し、古い応答の上書きを防ぎます。

## コストと運用上の制限

アプリケーションの結果サイズとメモリ割り当ては、履歴件数ではなくプロバイダー数に依存します。SQL集計と正確な中央値には該当履歴の走査やソートが必要で、DB負荷は定数ではありません。期限、キャッシュ、同時更新の共有で実行時間と重複負荷を制限します。各レプリカは個別のキャッシュを持ちます。タイムアウト中も基本一覧は利用できます。DB負荷が続く場合、増分集計やインデックスを別途設計する必要があります。今回は近似値や任意の行数制限を導入しません。

更新完了後の観測集計は最大15秒間キャッシュされます。スキーマ移行、環境変数、デプロイ設定、`/v1`契約の変更は不要です。ロールバックは以前のアプリケーション版に戻します。

## 検証

- SQLiteとPostgreSQLで旧メモリ計算との一致を確認。UTC境界、古い観測、不明な観測元、将来日時、失敗、偶数件の中央値を含みます。
- 大量の合成履歴で返却行数の上限を確認し、10,000件と100,000件で時間と割り当て量を計測します。
- キャッシュ再利用、期限切れ、プロバイダー集合変更、同時更新、キャンセル、エラー再試行、認可、内部情報を隠した失敗応答を検証します。
- ブラウザーシナリオ `providers independent-monitoring-success` と `providers independent-monitoring-failure` で、監視の遅延や失敗が一覧をブロックせず、成功後に監視状態を更新できることを検証します。
- `providers cancels-obsolete-monitoring` で、画面遷移時に古いリクエストをキャンセルし、戻った画面の新しい監視状態を維持することを検証します。
