# 管理概要とアラート履歴

概要はメタデータ件数、プロジェクト、Provider 設定、最新 20 件のアラートを返します。完全なモデル定義は必要な画面で読み込みます。モデル検索は `GET /api/admin/model-search?q=...` を利用し、最大 20 件を返します。

## 過去の統計

`GET /api/admin/overview` の全保持期間の使用量とリクエスト合計は `overview_totals` から読み取ります。SQLite の全体合計は 2 行です。PostgreSQL はトランザクションごとに非ブロッキング advisory lock で異なるシャードを予約し、読み取り時に寄与を合計します。シャード数は書き込みのピーク同時実行数に応じます。修正による正負の寄与を保持するため、内訳の絞り込みはシャード間集計後に行います。全期間の内訳も同じ投影のモデル、Provider、リソース次元を利用し、概要メタデータと独立して読み込みます。権限別集計はプロジェクト、API key、帰属ユーザーの組を維持し、OR 条件が重複しても各記録を一度だけ数えます。独立した `GET /api/admin/usage/summary` は従来の SQL 集計を維持します。期間レポートと時系列は既存の期間と分析クエリを使用します。

SQLite のマイグレーション 12 と PostgreSQL の 13 は集計表、元記録の投影マーカー、インデックス、トリガーを追加します。挿入、関連フィールドの修正、削除は同一データベーストランザクションで集計に反映され、現在の Go プロセス以外の書き込みも対象です。各記録は一度投影され、修正時は以前の寄与を減算して新しい寄与を加算します。

既存記録はデータバックフィル ledger によりオンラインの制限付きバッチで処理します。未処理マーカーのインデックスが永続カーソルになります。各バッチは集計、処理済みマーク、処理件数を同一トランザクションで保存します。クラスタ lease が複数インスタンスを調整し、終了時は処理を取り消して自身の lease を解放します。既存のバックグラウンドスケジューラがワーカーを起動します。PostgreSQL のマイグレーション 14–17 は索引ごとの並列構築、再試行、厳密な事後検証を行います。共通マイグレーション 18 は永続完了状態を追加し、完了後の履歴探索を省きます。

バックフィル中も概要画面を利用でき、`summary_status.state` は `preparing` です。全体運用権限では処理件数、制限されたユーザーには準備状態を表示します。更新が完了してから 3 秒後に次の更新を開始し、両データソースの処理が完了すると完全な合計を表示します。新規データベースでは直ちに完全な統計を提供できます。

正常な集計は有効な権限範囲ごとに 15 秒キャッシュされ、同時更新はクエリを共有します。個別キャンセルは待機を終了し、最後の待機者が共有処理を取り消します。権限範囲のキャッシュは最大 128 件、クエリ期限は 10 秒です。更新失敗時は最大 60 秒前の成功結果を `stale` と計算時刻付きで返せます。それを超えると統計領域に独立したエラーを表示し、他の画面データは利用できます。内訳の取得に失敗した場合は古い内訳を消去してエラーを表示します。準備中の場合は古い内訳を消去し、概要の準備状態を表示します。

SQLite のマイグレーション 19 は、レコードを置き換える際に元の寄与を差し引きます。再帰トリガーが既定の設定の外部接続にも適用されます。旧概要版からのアップグレード時には既存の全体投影の件数を一度検査し、不一致の場合は権限範囲内の元データを集計します。マイグレーション 20 は `db prepare` または `db migrate` の完了前に両バックフィルを登録し、空のデータソースは完了として記録します。PostgreSQL の並行インデックス作成は現在のスキーマを対象とし、同名で定義が異なる場合は停止します。

タイムアウト時に直近の成功結果を使用できる上限も 60 秒です。トレンドとランキングには各クエリの結果を表示し、取得失敗時はそのパネルのデータを消去します。Provider の割合は全 Provider の総コストを基準にします。チームリーダーは有効なルートがある稼働中のモデルを参照でき、セキュリティ管理者は監査とゲートウェイの画面でモデルの選択肢を利用できます。

## アラート履歴

`GET /api/admin/alerts` は `data`、`page`、`page_size`、`total` を返します。既定は 50 件、上限は 100 件です。`project_id`、`severity`、`from`、`before` を指定できます。日時は RFC 3339 形式で、`from` を含み `before` を除きます。作成日時と ID の降順です。

履歴画面はサーバーページングと古いリクエストの取り消しを行い、フィルター後の総数と現在ページの件数を区別します。履歴の削除で現在ページがなくなった場合は、有効な最後のページを再取得します。プロジェクトのクォータイベント件数と最終発生時刻は `GET /api/admin/project-quota-events` から取得し、可視プロジェクトの保持済み履歴を集計します。全体運用権限ではリクエストログとアラートの合計を返し、制限されたユーザーには有効な権限内のリクエストログの集計のみを返します。

任意の `q` は、件数取得とページ分割の前に、ID、イベントコード、メッセージ、スコープ、重大度、リソース、日時の文字列に一致するアラートを抽出します。プロジェクトで絞り込むと、そのプロジェクトの直接のアラート、API キーとユーザーのクォータアラート、および保存済み設定で識別できるプロジェクト予算のアラートが含まれます。

## 検証

バックエンドテストは応答上限、フィルター、権限の重複、修正、削除、再開可能なバッチ、キャンセル、古いキャッシュの期限を検証します。PostgreSQL 投影テストは CI でも実行します。`overview-bounds` UI シナリオは正常、準備中、失敗、モデル検索、履歴ページングを対象とします。

任意実行の `TestOverviewRepresentativeScale` と `TestPostgresOverviewRepresentativeScale` は使用量 300 万件、リクエスト 300 万件、アラート 10 万件、モデル 300 件を用意します。バックフィル完了後、冷たいキャッシュと温かいキャッシュを 10 並列で測定し、p95 と要求当たりの累積割り当て量を記録して p95 が 1 秒未満であることを確認します。`TOKENHUB_OVERVIEW_SCALE=1` を設定してください。PostgreSQL には `TEST_POSTGRES_URL` と `integration` build tag も必要です。使用量とリクエストの日時は 2026-01-01 に固定され、現在の直近トレンド期間は空です。結果は過去の投影読み取りと空の直近トレンドクエリを対象とし、データのある直近トラフィックのクエリやライブ書き込みのスループットを証明しません。測定値は固定テスト環境に対応し、本番のピーク RSS と過去の OOM の原因には現場の証拠が必要です。

SQLite の金額投影は補償加算で小さい寄与を保持します。合計が SQLite の整数範囲を超えた場合や金額の累計が有限値でなくなった場合は、キャッシュと期限を維持したまま元の SQL 集計に戻り、元記録と修正後の正確性を守ります。この例外経路は履歴を走査します。PostgreSQL の集計は NUMERIC を使用します。

既存の v0.11.0 ランナーは新しい ledger エントリーを拒否します。アップグレード後のアプリケーションロールバックには、マイグレーション 20 まで検証できる互換ブリッジ版を事前にデプロイする必要があります。管理フロントエンドも同時に更新してください。
