# 時間帯とキャッシュの料金

## 現在の動作

モデルと Provider モデルの料金時間帯は `weekdays`（0 が日曜、6 が土曜）、IANA タイムゾーン、RFC3339 の有効期間、通常入力・キャッシュ読み取り・通常/5 分/1 時間キャッシュ書き込み・出力の単価上書きに対応します。曜日省略時は毎日です。日をまたぐ時間帯は開始曜日に属し、開始を含み終了を含みません。開始と終了が同じ場合は選択日の終日です。

時間帯は最大 64 件です。有効期間が交差する週次時間帯の重複は拒否し、同じタイムゾーンを要求します。それ以外の時間には既定価格を使います。時間帯の単価省略は継承、明示的なゼロは無料です。

モデルカタログでキャッシュ読み取り価格をゼロにすると、保存・再読込後も無料です。モデル HTTP PATCH で省略した価格は保持します。`cache_read_price_usd_per_1m: null`、またはゼロ単価と `metadata.cache_read_price_configured: "false"` により従来の推定へ戻せます。無関係なメタデータ更新は無料状態を取り消しません。キャッシュ書き込み PATCH のゼロは無料、null は継承です。割引は実 Token クォータや TPM を減らしません。

従来のテナント料金は受付時の価格を使います。共通ルーティングの Provider 試行は送信前にモデル設定を固定し、処理中の価格変更で当該コストを再計算しません。新しい証拠は Provider 価格の欠落を明示し、既知のコストを捏造しません。

## 精密なシャドー料金

プラットフォーム管理者は「請求 → 精密料金計算とシャドー照合」でテナントモデルまたは Provider/モデルを選択し、十進文字列の単価と時間帯を設定し、指定時刻の料金をプレビューして不変のシャドー版を公開できます。フォームではプレビュー成功を要求し、変更すると古いプレビューを無効にします。各時間帯で少なくとも 1 日を選択してください。

シャドー料金は新しいリクエストの比較記録用で、現在の請求や予算予約を置き換えません。従来設定は `legacy_float_configuration` として識別し、十進文字列への変換を過去の精密根拠とみなしません。アダプターの usage フィールド存在性と Provider の課金時刻ルールは未確認です。矛盾、価格・usage 欠落、配信の不確実性は確認待ちとして保持します。供給者請求との照合済みを意味しません。

単価は整数部最大 18 桁、小数部最大 12 桁です。正確な分項を合計後、half-even で 12 桁へ一度丸めます。換算には丸め前の合計を使い、為替不明なら元通貨額を保持し USD を省略します。テナントは USD で、現時点では基本 6 分項すべてが必要です。独立した「適用外」状態は未対応です。

以下はプラットフォーム管理者専用です。

| メソッド | パス | 用途 |
| --- | --- | --- |
| GET, POST | `/api/admin/billing/rate-cards` | 不変シャドー料金の一覧・公開 |
| POST | `/api/admin/billing/preview` | `{card, at, usage, exchange_rate}` のプレビュー |
| POST | `/api/admin/billing/exchange-rates` | `{currency, rate, source, effective_from?}` を公開。元通貨 1 単位 = `rate` USD |
| GET | `/api/admin/billing/evidence/{request_id}` | 受付・試行準備・シャドー精算の証拠 |

料金には `kind`（tenant/provider）、`target`（モデル名または `provider_id:upstream_model`）、`currency`、`source`、任意の `effective_from`、`rates`、任意の `periods` を含めます。分項キーは `input`、`cache_read`、`cache_write`、`cache_write_5m`、`cache_write_1h`、`output` です。時間帯は時間ルールと `rates` 上書きから構成します。適用可能な最新の有効時刻を選び、同じ DB 時刻に即時公開された版は revision で順序付けます。過去のスナップショットは元の版を保持し、為替は試行ごとに固定します。料金・為替の公開は管理者監査に記録します。

証拠にはプロジェクト/Key の ID と名称、ユーザー/チーム/コストセンター ID、受付 UTC 日/月、試行ごとの Provider/リソース、価格、為替、上流リクエスト ID と結果を保存し、prompt、応答本文、認証情報は保存しません。準備のみで完了証拠がない試行は「送信された可能性あり」であり、自動再送や無料扱いは禁止です。シャドー精算は既存精算と同一トランザクションで、サーバーリクエスト ID ごとに基本記録を 1 件だけ作成します。

## 移行と残作業

DB 拡張 4 は `metering_entries` と索引を追加し、過去の usage と基線マイグレーションを書き換えません。実行時はスキーマ 4 が必要で、通常の起動で旧 DB を更新します。復元・ロールバックでは証拠テーブルと互換バイナリが必要です。自動的な証拠保持期限の削除は未実装です。

今回は料金とシャドー証拠の増分です。全範囲の永続金額予約、実際の精密課金、プロトコルのフィールド存在性、障害復旧と 24 時間の手動確認キュー、不変調整、一般ユーザー向け証拠、適用外分項、既存照合との接続は後続作業です。予約丸めヘルパーはテスト済みですが受付制御には未接続です。共通試行ループを通らないバックグラウンド経路には同等の証拠がまだありません。本番 PostgreSQL 並行性と供給者請求一致は未検証です。

モデル価格の更新では、有限でない基本単価や負の基本単価を拒否します。設定の根拠がない従来の Provider のゼロ値は、継承されたキャッシュ書き込み価格も含め、使用量の項目ごとに不明として扱います。明示的なシャドー料金表または時間帯の上書きでは無料を指定できます。正確な料金表でシャドー料金を計算できても、従来価格の根拠がなければ `legacy_usd` は空のままです。`tokenhub db verify` は証拠テーブルとインデックスを含む拡張後の構造を検証し、既存データベースの採用には変更されていない過去のベースラインを使用します。
