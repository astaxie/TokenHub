# 预留预算，并将上游重试成本与租户费用分开结算

并发请求只检查已累计费用，会同时消耗同一份剩余预算；平台重试则可能让一次租户调用产生多次供应商费用。2026-09-05 第三轮访谈确认在准入时原子检查并预留预算，结束后按用量结算；预留不足时拒绝请求，不静默缩短输出。此处为预算控制，不引入充值钱包。

供应商成本按每次上游调用尝试分别记录，租户只计一次实际交付对应的用量，不承担平台内部失败重试。缺失 usage 或缓存分项时保留待核实状态和估算依据，不将未知视为零，不将估算冒充最终费用，补齐证据后通过调整记录修正。

租户在平台准入时锁定价目和峰谷时段，整次请求保持一致。上游按供应商规则确定时间依据；DeepSeek 时间依据未确认期间，以每次上游发送时点作显式估算并保留时间证据。这样牺牲了一部分预算利用率，并使平台承担失败重试成本，但避免并发重复使用预算和将内部容错成本直接转嫁给租户。

第四轮确认预留按所有可能收费分项在合法组合下的费用上界计算，包含可能更贵的缓存写入；严格预算缺少可靠上界时拒绝。确认未发送的失败释放预留，已发送但用量不明则保留占用，超过 24 小时告警并转人工处理，不自动清零或转最终消费。租户费用、预留和后续调整归准入时锁定的 UTC 日/月周期。

部分交付按可确认用量收费，其余待核实；客户端主动重发默认是新调用，首期不新增响应重放型幂等 API。设计决定不代表当前实现已具备这些保障，完整方案见[设计稿](../discussions/2026-09-05-time-cache-billing-design.md)。
